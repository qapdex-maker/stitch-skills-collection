## 2026-03-03 - Path Traversal in Local Resource Inlining
**Vulnerability:** In post_process.ts, the function resolveLocalFile resolved local paths parsed from HTML/CSS files without validating if they traversed outside of the safe baseDir or project root, permitting arbitrary local file read.
**Learning:** Functions that parse and inline local file references (like src attributes or CSS url() patterns) are susceptible to Path Traversal (CWE-22) if they resolve paths using path.join or path.resolve without checking absolute containment against a designated safe root.
**Prevention:** Always resolve the absolute paths of both the target file and the safe root, and verify that the target path is equal to the root path or starts with the root path followed by the directory separator (e.g. absolutePath.startsWith(absoluteRoot + path.sep)).

## 2026-03-04 - Defense-in-depth against Symlink Path Traversal Attacks
**Vulnerability:** Even if absolute paths are validated using `path.resolve` and `startsWith`, symlink/junction-based directory traversal attacks can bypass this validation if a symlink resides inside the safe root but points to a file outside it. When the file is later opened, the system follows the symlink and reads the external file.
**Learning:** Checking paths solely via `path.resolve` is vulnerable to symlink bypass. To protect against this, we must resolve canonical physical paths using `fs.realpathSync`.
**Prevention:** Resolve canonical physical paths of both the target file and the safe root via `fs.realpathSync` before validating containment. Fall back gracefully to `path.resolve` if `realpathSync` fails (e.g. because the file does not exist yet). Ensure that functions returning resolved local files return the canonical physical path to prevent MIME resolution bypass or subsequent file access outside boundaries.

## 2026-03-05 - Headless Browser Arbitrary Protocol Loading (LFI/SSRF)
**Vulnerability:** In snapshot.ts, the Puppeteer headless browser was directed to navigate to any URL string supplied as a command-line argument without protocol or scheme restriction, allowing local system file exposure (CWE-22/CWE-918) via `file:///etc/passwd` or script execution via `javascript:...`.
**Learning:** Utilities utilizing browser automation tools (like Puppeteer, Playwright, or Selenium) to capture snapshots, scrape HTML, or render PDFs must explicitly restrict loaded protocols. Merely verifying that an input is a valid URL is insufficient since `file:`, `gopher:`, and `data:` schemes are still valid URLs.
**Prevention:** Always parse inputs using the `URL` constructor and strictly whitelist permitted protocols (e.g., matching `parsed.protocol === 'http:' || parsed.protocol === 'https:'`) before initiating browser navigation.

## 2026-03-06 - Headless Browser and Shell Script SSRF/Protocol Redirection Protection
**Vulnerability:** The headless browser utility in `snapshot.ts` did not restrict navigation to standard non-metadata IP addresses, allowing Server-Side Request Forgery (SSRF) targeting cloud metadata services (e.g. `169.254.169.254`). Additionally, bash scripts used standard `curl` calls which allowed any arbitrary protocol scheme to be loaded.
**Learning:** Headless browser tools and external download scripts require rigorous URL/protocol constraints. While `snapshot.ts` must allow loopback (`localhost` / `127.0.0.1`) for local developer usage, link-local addresses (`169.254.169.254`, `[fd00:ec2::254]`, `fe80::/10`) should be explicitly blacklisted. Shell scripts using `curl` should restrict permitted protocols via `--proto =http,https` to prevent protocol-switching or Local File Inclusion (LFI).
**Prevention:** Apply a Link-Local and Cloud Metadata blacklist filter to browser navigations, and always use `--proto =http,https` when fetching remote resources in shell utilities.

## 2026-03-07 - SSRF Bypass via IPv4-mapped and IPv4-compatible IPv6 Addresses
**Vulnerability:** URL validation routines (`isSafeUrl`) in `snapshot.ts` and `extract_inline_html.ts` attempted to block link-local/metadata IP addresses, but only checked direct IPv4 strings (e.g., `169.254.169.254`) and specific IPv6 forms. Attackers could bypass these checks using IPv4-mapped or IPv4-compatible IPv6 representations (e.g., `[::ffff:169.254.169.254]` or `[::ffff:a9fe:a9fe]`), which are successfully processed by Node's URL parser but bypass simple string-based checks.
**Learning:** Simply checking `hostname` string equality is insufficient to prevent SSRF because IP addresses have multiple normalized representation formats, particularly when mapped into the IPv6 namespace. All parsed hostnames must be canonicalized to their decimal IPv4 format before checks are applied.
**Prevention:** Normalize IPv4-mapped and compatible IPv6 hostnames back to standard decimal IPv4 format (e.g., extracting and parsing the trailing hex/decimal parts) before verifying containment in restricted IP blocklists.

## 2026-03-08 - SSRF Protection Expansion for Carrier-Grade NAT, Benchmark, and Advanced IPv6 Address Ranges
**Vulnerability:** The SSRF validation filter `isSafeUrl` in `extract_inline_html.ts` blocked standard IPv4 private and link-local ranges, but omitted Carrier-Grade NAT (100.64.0.0/10), Benchmark testing (198.18.0.0/15), Multicast (224.0.0.0/4), Unique Local IPv6 (fc00::/7), complete Link-Local IPv6 (fe80::/10), and Multicast IPv6 (ff00::/8) address spaces. This allowed potential SSRF against internal services residing on these subnets.
**Learning:** Robust SSRF prevention must cover all private, local, multicast, and benchmarking IP allocations defined by IETF RFCs across both IPv4 and IPv6 families, rather than just standard loopback/private/metadata ranges.
**Prevention:** Apply a comprehensive list of IPv4 address boundary checks and use precise hex/digit-based regular expressions for IPv6 families to catch all non-routable, multicast, link-local, and unique-local scopes.

## 2026-03-09 - IPv6 Link-Local SSRF Blocklist Bypass via prefix-based matches
**Vulnerability:** In `snapshot.ts`, the URL validation routine `isSafeUrl` blocked standard cloud metadata addresses and IPv6 link-local addresses but only verified if the hostname started with exactly `"fe80:"`. This omitted other parts of the standard IPv6 link-local block (`fe80::/10`) such as `fe90::/10`, `fea0::/10`, and `feb0::/10`, allowing potential SSRF against services residing on these link-local subnets.
**Learning:** Simple string prefix checks like `startsWith('fe80:')` are insufficient for IPv6 address ranges since addresses can fall under wider prefix allocations (like `/10` subnetting).
**Prevention:** Always use precise hex/digit-based regular expressions (e.g. `/^fe[89ab][0-9a-f]:/i`) to block entire prefix-allocated subnets like `fe80::/10` across all services.

## 2026-03-10 - SSRF URL Validation Bypass via GCP Metadata DNS Names and Subnet Omissions
**Vulnerability:** The SSRF validation routines in `snapshot.ts` and `extract_inline_html.ts` did not validate or block the standard GCP metadata server DNS hostnames (`metadata.google.internal` / `metadata`). Furthermore, `snapshot.ts` only blocked a single IPv4 address (`169.254.169.254`) instead of the entire link-local `169.254.0.0/16` subnet, permitting potential SSRF bypasses via custom local routes.
**Learning:** SSRF URL filters must explicitly block both metadata IP subnets (e.g., the entire `169.254.0.0/16` range) and the corresponding cloud provider DNS hostnames since modern cloud APIs and environments resolve metadata hosts through internal DNS search paths.
**Prevention:** Explicitly match and block cloud-specific DNS names like `metadata.google.internal` and `metadata`, and perform subnet/prefix checks on the entire `169.254.0.0/16` IPv4 address block instead of individual addresses.

## 2026-03-11 - SSRF Redirect and Subresource Bypass in Headless Browser via Request Interception Lack
**Vulnerability:** In `snapshot.ts`, validation of the URL was only performed statically before initiating browser navigation. Once navigation started, the browser could follow standard HTTP redirects or load subresources/iframes pointing to unsafe internal IP addresses or cloud metadata endpoints (e.g. Alibaba Cloud IMDS at `100.100.100.200` or Azure IMDS at `instance.metadata.azure.com`), bypassing static validation entirely.
**Learning:** Standard static validation of a target URL is insufficient for headless browsers or scrapers because they dynamically resolve and follow redirects and load nested dependencies (scripts, stylesheets, iframes). Robust protection requires real-time network request interception at the browser engine level.
**Prevention:** Always enable request interception (`setRequestInterception(true)`) in headless browser instances, intercept all outgoing requests, and abort those that violate `isSafeUrl` constraints while allowing local protocol handlers (like `data:`, `blob:`, and `about:`) to function normally.

## 2026-03-12 - Inconsistent Cloud Metadata SSRF Filters and Provider Omissions
**Vulnerability:** The SSRF validation filter `isSafeUrl` in `extract_inline_html.ts` omitted critical cloud-provider metadata hostnames (such as Azure's `instance.metadata.azure.com`) that were present in `snapshot.ts`. Additionally, both filters lacked explicit blocks for high-risk virtual and metadata IPs used by Oracle Cloud (`192.0.0.192`) and Azure (`168.63.129.16`), leaving systems running these tools vulnerable to targeted SSRF.
**Learning:** SSRF filters across multiple utility files must be strictly aligned and synchronized. Discrepancies in metadata blocklists across similar components can easily lead to bypasses. Additionally, non-traditional cloud metadata services (e.g., OCI's metadata endpoint or Azure's virtual IP) do not fall under standard private/RFC1918 subnets, necessitating explicit host/IP blocking.
**Prevention:** Align SSRF filter implementations across all network-facing utilities and explicitly block all cloud-specific metadata/virtual service IPs alongside standard loopback, link-local, and private subnets.

## 2026-03-13 - Command Option Injection and Protocol Hijacking in Download Shell Utilities
**Vulnerability:** Shell-based downloader utilities (`fetch-stitch.sh` and `download-stitch-asset.sh`) passed user-supplied URL and output path parameters to `curl` without sanitization. An attacker supplying options (e.g., prefixing arguments with `-`) could execute Option Injection (CWE-88), hijacking command-line flags. Additionally, lack of early protocol-level validation could permit protocol redirection or SSRF.
**Learning:** External command-line utilities (like `curl`) called inside scripts are vulnerable to Option Injection if parameter bounds are not strictly enforced. Validating protocols beforehand and separating positional arguments using the `--` option terminator protects system calls from argument parsing ambiguity.
**Prevention:** Always restrict URL parameters at the shell script boundary using regex-based protocol matching (e.g. `^https?://`), reject outputs starting with hyphens (`-*`), and use the `--` end-of-options marker in command-line invocations.

CLI scripts should also sanitize parameters that construct request paths (like project ID) to prevent URL/endpoint injection.
**Prevention:** Use absolute path resolution and prefix containment checks on the output directory and each file destination. Normalize path separators (like converting backslashes to forward slashes) for robust cross-platform path validation, and validate CLI input fields against safe alphanumeric regex patterns.

## 2026-03-15 - SSRF Blocklist Discrepancies and IPv6 ULA/Multicast Omissions in Snapshot
**Vulnerability:** The Puppeteer-based snapshot utility `snapshot.ts` possessed an incomplete `isSafeUrl` implementation that permitted Unique Local Addresses (fc00::/7), multicast (ff00::/8), and unspecified (::) IPv6 addresses. ## 2026-03-16 - Path Traversal and Arbitrary File Write in CLI Snapshot Output
**Vulnerability:** In `snapshot.ts`, the parameter `--output` was used to write a snapshot file directly to the local disk without validating that the target path resided within the safe workspace boundary (CWD), permitting potential directory traversal and arbitrary file write/overwrites (CWE-22) in automated/MCP environments.

## 2026-03-17 - Arbitrary File Write in Downloader Shell Scripts

## 2026-03-18 - Symlink Directory Junctions and Path Traversal in Multi-Page HTML Destination Paths
**Vulnerability:** In `extract_inline_html.ts`, the destination file names for extracted pages were resolved and validated using `path.resolve` relative to the output directory, but did not resolve symlinks or junctions to their canonical physical paths. This left the system vulnerable to symlink directory traversal attacks (CWE-59 / CWE-22), where a symlink could point outside of the designated output directory and lead to arbitrary file write.
**Learning:** Checking destination paths solely via `path.resolve` is vulnerable to symlink-based traversal bypasses. To resolve this, we must check containment using canonical physical paths resolved with `fs.realpathSync`. Additionally, wrapping the main execution block in an `isMain` block check prevents full CLI script execution when importing functions for unit tests.
**Prevention:** Resolve canonical physical absolute paths of both the target destination and safe root using `fs.realpathSync` before checking containment, falling back to parent directory realpaths or unresolved paths when the files do not exist yet. Normalizing separators and performing case-insensitive checks on Windows ensures robust cross-platform security.
